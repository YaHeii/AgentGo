# internal/ui 开发约定

日期：2026-06-02

## 目标与范围

本文档只记录 `internal/ui/` 这一层当前应长期遵守的开发约定。

它的目标是帮助后续协作者在修改 UI 时，先统一边界，再决定实现方式。本文档偏向稳定约定，而不是当前实现说明。

本文档回答以下问题：

- `internal/ui/` 对系统负责什么，不负责什么
- `common`、`model`、`xchroma` 各自应该承载什么类型的代码
- UI 层在事件、状态、组件复用、ANSI 处理上的默认做法
- UI 改动后的最小验证动作是什么

本文档不承担以下职责：

- 不复述仓库通用分层规范；项目级通用约定仍以 [AGENTS.md](/root/agentGo/AGENTS.md) 为准
- 不记录容易频繁变化的实现细节，例如具体字段名、布局常量值、临时交互策略
- 不把当前 UI 代码写成逐文件使用手册

## UI 层总体边界

- `internal/ui/` 负责终端界面的呈现、局部交互状态、全局输入事件路由，以及把用户动作转成对 `app` facade 的调用
- `internal/ui/` 不负责业务编排，不持有 `session`、`message`、`agent` 的领域真相源
- UI 层不直接访问 `db`、`provider`、store 或其他基础设施实现
- UI 看到的业务变化，应优先来自 `app` 暴露的方法和统一事件流，而不是自己跨层拉数据
- UI 内部允许存在只服务显示和交互的本地 projection/state，但这些状态不能反向定义领域语义

## 子目录边界

### `internal/ui/model`

- 负责终端 UI 的状态组织、事件路由、布局计算和组件协作
- 这里可以持有 UI-local state，例如 viewport、展开折叠、输入缓冲、瞬时状态、命中区域映射
- `ui.go` 是当前唯一的 Bubble Tea 顶层状态机；它的职责固定为“全局事件接收、区域命中、局部坐标转换、子组件路由、向 `app` 发动作”
- 除 `ui.go` 外，其余组件默认保持为普通结构体，不向下继续嵌套 `tea.Model`
- `model` 不应沉淀与终端框架无关的通用文本处理工具，也不应下沉到底层样式/ANSI 基础设施实现

### `internal/ui/common`

- 负责可复用但无业务归属的展示辅助能力
- 适合放无状态 helper，例如 markdown 渲染、展示格式化、小型文本工具
- `common` 不应依赖 `UI`、`Chat`、`Header` 等具体模型，也不应持有交互状态

### `internal/ui/xchroma`

- 负责底层样式、高亮相关的适配或封装
- 它的定位更接近展示基础设施，而不是 UI 编排层
- `xchroma` 可以被 `common` 或 `model` 使用，但不应反向依赖 `model`，也不应持有交互状态

## 组件与状态约定

- `ui.go` 负责顶层编排；子组件负责自己的局部状态和局部渲染
- 若状态只为某个组件的显示或交互服务，应优先留在该组件内部，不要上提到 `UI`
- 若事件需要跨区域分发、命中判断或坐标转换，应由 `UI` 统一处理后再下发
- 顶层可以直接修改子组件或局部状态时，不要为了“看起来标准”额外引入 `Cmd`
- 保持简洁；不要为了单次需求提前引入嵌套模型、事件总线或多余抽象
- 如有必要，可以创建独立文件分离局部逻辑；但拆分的依据应是职责边界，而不是文件数量

## 组件复用与样式约定

- UI 实现应优先复用 charm.land 提供的成熟组件和样式能力，而不是手写重复部件
- 默认优先考虑：
  - `charm.land/bubbles/v2`
  - `charm.land/huh`
  - `charm.land/lipgloss/v2`
- 只有在现有组件无法覆盖需求、或引入后会明显增加复杂度时，才考虑自定义实现
- 自定义实现应尽量复用现有组件的布局、样式或交互约定，避免在同一 UI 层内形成多套体验

## ANSI 与字符串处理约定

- 凡涉及 ANSI 码的字符串操作，必须优先使用 `github.com/charmbracelet/x/ansi`
- 不要在字节层面直接截断、切片或估算带 ANSI 的字符串
- 需要裁剪、测宽、去样式或截断时，优先考虑以下函数：
  - `ansi.Cut`
  - `ansi.StringWidth`
  - `ansi.Strip`
  - `ansi.Truncate`

## Update 与 Cmd 约定

- 不要在 `Update` 中执行 IO 操作或耗时任务；这类工作必须通过 `tea.Cmd` 发起
- 不要在 `Cmd` 内部直接修改模型状态；`Cmd` 只负责产出 `Msg`，状态更新必须回到主 `Update` 循环完成
- 如果某个变化可以直接在当前调用栈中修改子组件或局部状态，就不要再额外发送消息绕一圈
- 只有当操作需要异步执行、等待外部结果或显式回到主循环时，才引入 `Cmd`

## 最小验证约定

- UI 改动完成后，默认至少运行：

```bash
GOCACHE=/tmp/go-build /usr/local/go/bin/go test ./internal/ui/model -count=1
```

- 如果改动影响到 `common` 或其他展示辅助能力，应补充运行对应包的定向测试
- 在边界调整或文件迁移时，应更频繁地运行定向测试，不要攒多步后再一次性修复
